# v1.13.0 Follow-ups — carried into v1.14.0

Recorded 2026-07-28, at the close of v1.13.0 "Presence & Mentor". These are the open items the
release surfaced but did not fix. Each says what was verified, so the next author does not have
to re-derive it.

## 1. ~~`TranslationServer` has no signals — `LocaleChanged` is a real defect~~ — RESOLVED

**Closed 2026-07-28** in PR #14 review. Copilot independently flagged the same defect, which
prompted a second look at the replacement API. Confirmed against
[`scene/main/node.h` @ 4.3](https://raw.githubusercontent.com/godotengine/godot/4.3/scene/main/node.h):

```cpp
NOTIFICATION_TRANSLATION_CHANGED = MainLoop::NOTIFICATION_TRANSLATION_CHANGED,
```

`Node` inherits the constant from `MainLoop`, so the fix is `_notification` / `_Notification`
rather than a signal subscription — which also deletes the subscribe/unsubscribe boilerplate and
the leak it was guarding against. `rtl-support.md` now shows both GDScript and C#, and the
`localization` summary was corrected. The original finding is kept below for provenance.

### Original finding

**Where:** `skills/localization/references/rtl-support.md` (the `LocaleAwarePanel` C# example)

```csharp
TranslationServer.Singleton.LocaleChanged += ApplyLayoutForLocale;   // does not exist
TranslationServer.Singleton.LocaleChanged -= ApplyLayoutForLocale;
```

**Verified:** the Godot class reference for `TranslationServer` has **no Signals section at all**
— checked on both [stable](https://docs.godotengine.org/en/stable/classes/class_translationserver.html)
and [latest](https://docs.godotengine.org/en/latest/classes/class_translationserver.html). The
class exposes properties and methods only.

**Origin:** inherited from the v1.8.0 C# parity push, not introduced by v1.13.0. The v1.13.0
review caught it because the refactor promoted the claim into a SKILL.md summary; that summary
was corrected, the reference code was left alone.

**Not fixed here because** the replacement API was not confirmable in the time available — the
`Node` / `Control` constant lists were truncated in the fetched docs, so substituting
`NOTIFICATION_TRANSLATION_CHANGED` would have swapped one unverified call for another. Confirm
against the engine source or a running 4.3 build before editing, then fix the reference and the
paired GDScript if it has the same shape.

## 3. ~~Cursor and Copilot CLI hook delivery is unverified~~ — RESOLVED for Copilot, OPEN for Cursor

**Copilot closed 2026-07-31.** Verifying it found a defect that made the hook fail on *every*
Copilot session on Windows, so the item was never merely unconfirmed — it was broken.

**Copilot CLI executes the `command` key through PowerShell on Windows.** PowerShell parses a
leading quoted path as a *string expression*, not a command, so the shipped
`"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.cmd" session-start` failed before running:

```
ParserError: Unexpected token 'session-start' in expression or statement.
Hook from "godot-prompter@skillsmith" execution failed: Hook command failed with code 1
```

Three things measured rather than assumed, each of which changed the fix:

1. **Copilot's hook schema takes per-shell `bash` / `powershell` keys and prefers them over
   `command`** ([hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference)).
   Confirmed by probe: a hook carrying all three logged `POWERSHELL_KEY_USED`. So the fix adds
   keys rather than rewriting the shared `command`, and Claude Code is untouched.
2. **Copilot expands `${CLAUDE_PLUGIN_ROOT}` inside the `powershell` key before handing the
   string to PowerShell** — probed, returns the real path. The `$env:` form would have been
   wrong; `${…}` is also valid PowerShell variable syntax, so guessing here would have produced
   a silent empty path instead of an error.
3. **`COPILOT_CLI=1` *is* exported to hook processes**, alongside `CLAUDE_PLUGIN_ROOT`,
   `COPILOT_PLUGIN_ROOT`, `PLUGIN_ROOT` and `COPILOT_PROJECT_DIR`. The existing output-shape
   branch (`additionalContext` vs Claude's `hookSpecificOutput`) was therefore already correct —
   worth checking, because had it not been, fixing only the parse error would have left the card
   silently discarded.

Verified end-to-end: Copilot, asked with tools disabled, answered "GodotPrompter is active…
Godot 4.7 with the Mobile renderer" — matching `config/features` in a project it could only have
learned about from the injected card.

**Upstream:** Superpowers ships the identical `command`-only shape and fails the same way on
Windows Copilot (`superpowers@superpowers-marketplace … code 1`, same ParserError). Worth
reporting to obra/superpowers — GodotPrompter's wrapper was adapted from it.

### Still open — Cursor

`hooks/hooks-cursor.json` is registered via `.cursor-plugin/plugin.json` and remains unconfirmed.
Two things to check when someone verifies it, both visible from the file alone:

- its command is **relative** (`./hooks/run-hook.cmd session-start`), which resolves only if
  Cursor sets the plugin root as CWD — Claude Code and Copilot both pass an absolute
  `${CLAUDE_PLUGIN_ROOT}` instead;
- if Cursor also uses PowerShell on Windows, the unquoted relative form happens to parse (a bare
  token is command-mode), but any plugin path containing a space would reintroduce the bug.

## 5. ~~Parity enforcement now has a blind spot~~ — RESOLVED

**Closed 2026-07-31.** `validate-skills.mjs` now walks `skills/*/references/*.md` and reports
under `csharp-parity-missing-reference` / `csharp-parity-accepted-reference`. Warning-level, like
the SKILL.md check, so CI is unaffected (`process.exit(errors.length > 0 ? 1 : 0)`).

**The blind spot was far larger than estimated below.** Measured before the fix: not six sections
across four skills but **166 zero-code sections across 42 of the 55 skills**, reaching 174
reference files. Six releases of Pattern X had made linking-out the dominant structure, so the
exception had quietly become the rule. Corroborating evidence: the parity debt list calls
`addon-development` "the first skill with fully closed C# parity", yet
`references/testing-plugins.md` still has a GDScript-only section — the debt was marked closed
*because* it moved to `references/`.

Three things the implementation had to handle, each found by measuring rather than assuming:

1. **Scope.** Walking only references reachable from a zero-code section and walking *every*
   reference produce an identical real-warning count, so the broad scan won — simpler, and it
   covers references before they are linked.
2. **Files sectioned by language.** `## GDScript` / `## C#`, `## Dash (GDScript)` / `## Dash (C#)`,
   `### State Machine — GDScript` / `### … — C#`. Applying per-section parity there gave a 31%
   false-positive rate (5 of 16), and "fixing" them would have meant restructuring correct files.
   Those fall back to file-level parity. The guard is strict on purpose: `## Connecting without
   disconnecting in C#` mentions C# but is a topic, not a partition, and still gets checked.
3. **Heading depth.** 11 references section at `### ` under a single H1, and 2 have no headings
   below the H1 at all. Splitting everything at `## ` skipped all 13 silently. The splitter now
   picks the shallowest level present and falls back to a whole-file check when there is none.
   Coverage is now 161/161 GDScript-containing references.

Result: **16 new `csharp-parity-missing-reference` warnings**, each hand-verified as a genuine
gap — `event-bus/anti-patterns.md` ×3, `godot-optimization/{cpu-bottlenecks,physics-tuning}.md`
×2 each, `localization/rtl-support.md` ×2, `mobile-development/plugins.md` ×2, and one each in
`addon-development/testing-plugins.md`, `animation-system/common-recipes.md`,
`event-bus/typed-signals.md`, `godot-optimization/draw-calls.md`,
`mobile-development/iap-and-ads.md`. Some may be intentionally single-language; each resolves as
*write the C#*, *extend `GDSCRIPT_ONLY_BY_DESIGN`*, or *restructure*. That triage is open work.

The byte budget was deliberately **not** extended to references — Pattern X exists to move
overflow there.

### Original finding

Six sections across `godot-ui`, `event-bus`, `multiplayer-basics`, and `localization` now contain
zero code blocks, because their GDScript/C# pairs moved wholesale into `references/`. The pairs
moved intact — the content audit confirmed no splits — but `validate-skills.mjs` only walks
`SKILL.md`, so `csharp-parity-*` passes vacuously for those sections and the parity evidence
lives somewhere the validator never looks.

Not a defect in v1.13.0. But as Pattern X continues, more parity moves out of reach. If parity
coverage is meant to stay enforced, the validator should walk `references/*.md` too.
