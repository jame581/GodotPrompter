# GodotPrompter v1.13.0 — "Presence & Mentor"

**Date:** 2026-07-27
**Baseline:** v1.12.0 (54 skills, validator 0 errors / 16 accepted warnings)
**Target:** 55 skills, first release shipping executable code

---

## Problem

Two problems, one release.

### Problem 1 — GodotPrompter loses the session to workflow plugins

When Superpowers (or any workflow plugin) is installed alongside GodotPrompter, GodotPrompter
skills go uninvoked during implementation. This was first observed in the DooGoo project on
2026-04-09 (all 35 commits used only Superpowers skills) and addressed in
`2026-04-09-superpowers-coexistence-design.md` by adding an assertive "MUST invoke" routing
table to `skills/using-godot-prompter/SKILL.md`.

**That fix underperformed, and the diagnosis explains why.** It treated the problem as one of
*wording* — passive bootstrap language losing to assertive language. The real difference is
*placement*:

| | Superpowers | GodotPrompter (v1.12.0) |
|---|---|---|
| SessionStart hook | yes — `hooks/hooks.json` | none |
| Bootstrap in context every session | yes — full SKILL.md inlined | only if the agent chooses to invoke it |
| Framing | `<EXTREMELY_IMPORTANT>` | — |
| Anti-rationalization table | yes — 12 rows | none |
| Cross-platform hook delivery | yes — `run-hook.cmd`, `hooks-cursor.json` | none |

Superpowers `cat`s its entire bootstrap skill into `additionalContext` on every
`startup|clear|compact` (`hooks/session-start:11,27`). GodotPrompter's equivalent guidance sits
in a file the model must *decide* to open — and by then the workflow plugin has already claimed
the turn. No amount of MUST/ALWAYS wording closes a placement gap.

**Compounding defect found during this audit:** 5 of 54 skills are absent from the bootstrap's
own category index — `ability-system`, `gdextension`, `gdscript-advanced`, `mobile-development`,
`multithreading`. The MUST-invoke routing table is staler still: 21 rows for 54 skills, omitting
all 5 third-party addon skills. **The router cannot route to skills it does not list.**

### Problem 2 — GodotPrompter can build, but it cannot teach

Every skill delivers finished code. Nothing explains *why* a node type was chosen, what to look
for when the scene is run, or what to do in the Godot editor — the GUI half of Godot development
that no skill in the repo currently covers.

---

## Goals

1. GodotPrompter domain skills are reliably invoked in Godot projects regardless of which
   workflow plugin drives the session.
2. A persistent **mentor mode** that teaches while building the user's own game, with editor
   guidance constrained to what is verifiable today and a clear path to full coverage.
3. Clear the pre-existing byte-headroom debt that would otherwise block any future contributor.

## Non-goals

- **No researched editor reference.** Full click-path editor guidance needs a Godot-release
  research cycle; deferred to v1.14.0. v1.13.0 ships a deliberately constrained Editor beat —
  see Change B4.
- No new third-party addon skills (GodotSteam, Dialogic remain deferred to v1.14.0).
- No raytracing skill — still deferred until the API stabilizes (~4.8+).
- No migration/upgrade meta-skill — deferred at v1.11.0, stays deferred.
- No slash commands — Claude Code / OpenCode only; the skill + config approach covers all
  7 platforms and a command would be additive sugar on top of it.
- No modifications to Superpowers.
- No minimum-version bump; the repo-wide Godot 4.3+ promise stands.

## Change A — The Presence Layer

### A1. SessionStart hook

New top-level `hooks/` directory:

```
hooks/
  hooks.json          SessionStart, matcher "startup|clear|compact"
  hooks-cursor.json   sessionStart variant (Cursor schema)
  run-hook.cmd        polyglot bash/cmd wrapper, Windows Git-Bash discovery
  session-start       extensionless bash script (see note below)
```

**Extensionless filename is deliberate.** Claude Code's Windows auto-detection prepends `bash`
to any command containing `.sh`, which double-invokes through the wrapper.

**Detection — conditional, not unconditional:**

```
walk cwd -> ancestors (max depth 4) looking for project.godot
  not found -> exit 0, emit nothing, silent no-op
  found     -> emit the session card
```

The hook is a no-op in every non-Godot repository. This is the deliberate difference from
Superpowers, which injects unconditionally: GodotPrompter is a domain plugin, and injecting
Godot routing into an unrelated repo is noise the user did not ask for.

**Output shape branches on environment**, matching the three consumer formats:

| Environment | Field |
|---|---|
| Cursor (`CURSOR_PLUGIN_ROOT` set) | `additional_context` (top-level, snake_case) |
| Claude Code (`CLAUDE_PLUGIN_ROOT` set, `COPILOT_CLI` unset) | `hookSpecificOutput.additionalContext` |
| Copilot CLI / SDK standard (fallback) | `additionalContext` (top-level) |

Claude Code reads both `additional_context` and `hookSpecificOutput` **without deduplication**,
so exactly one field must be emitted per platform.

Use `printf`, not heredocs — bash 5.3+ hangs on heredocs in this position
(obra/superpowers#571).

**Platforms without hooks:** Codex and Antigravity have no SessionStart mechanism. They continue
to inherit the bootstrap through the existing root `AGENTS.md` / `GEMINI.md` re-exports, which
are unchanged by this release.

**Attribution:** the polyglot wrapper, the bash-parameter-substitution JSON escaper, and the
three-way output branching are adapted from Superpowers (MIT, Jesse Vincent). This is credited
in a header comment in each adapted file and in the README's acknowledgements. We adapt openly
rather than reimplement quietly.

### A2. Inject a card, not the whole skill

`skills/using-godot-prompter/SKILL.md` is ~9 KB. Injecting all of it on every startup **and
every compaction** is a permanent context tax. Instead the hook extracts a delimited region:

```markdown
<!-- SESSION-CARD-START -->
...routing table + red flags + subagent clause...   (target <= 3 KB)
<!-- SESSION-CARD-END -->
```

The card lives *inside* the bootstrap skill, so it is a single source of truth and cannot drift
from the skill it summarizes.

**Validator support:** `validate-skills.mjs` gains a `session-card` check — both markers must be
present, correctly ordered, the enclosed region non-empty, and the region **at most 3,072 bytes**
(LF-normalized, consistent with the v1.12.0 measurement fix). Without the emptiness check, a
future edit could silently empty the hook payload while CI stays green; without the size cap,
the card grows unnoticed into a permanent context tax paid on every compaction. Fixtures under
`scripts/fixtures/` cover both failure cases, consistent with the validator self-test added in
v1.12.0.

### A3. Bootstrap hardening

Four changes to `skills/using-godot-prompter/SKILL.md`:

1. **Fix the category index** — add the 5 missing skills (`ability-system`, `gdextension`,
   `gdscript-advanced`, `mobile-development`, `multithreading`). Straight bug fix.

2. **Refresh the routing table** — 21 rows covering ~24 skills becomes full coverage of all 55,
   including the 5 third-party addon skills. This table is the injected card's payload, so its
   completeness directly determines routing quality.

3. **Add a Red Flags table** — Godot-specific anti-rationalization, modelled on Superpowers'
   12-row list:

   | Thought | Reality |
   |---|---|
   | "I know how CharacterBody2D works" | Knowing the class is not knowing the pattern. Invoke. |
   | "It's a two-line script" | Two-line scripts still pick node types. Invoke. |
   | "The plan already told me what to build" | The plan says what. The skill says how. Invoke. |
   | "I already loaded a Godot skill this session" | Different system, different skill. |
   | "The user just wants a quick fix" | Quick fixes set architecture. Invoke. |

4. **Sharpen the priority claim** — workflow plugins own *how you work*; GodotPrompter owns
   *what you build*. Both apply; neither supersedes the other.

**No `<SUBAGENT-STOP>` guard.** Superpowers uses one to stop its workflow skill hijacking
subagents. GodotPrompter wants the opposite — subagents writing Godot code *should* obey — so
the existing inclusive subagent clause is kept and strengthened.

### A4. Byte cost

All Change A edits land in `using-godot-prompter` (comfortably under budget) and in new `hooks/`
files. **Zero bytes are added to any of the 54 existing domain skills.** This is a hard
constraint, not an accident — see Change C for why.

## Change B — Mentor Mode

### B1. A delivery contract that wraps, never replaces

New skill: `skills/godot-mentor/SKILL.md` (54 -> 55 skills).

Mentor mode changes the *shape* of an answer, not its *source of truth*:

```
"add double jump"  +  mentor mode
        |
        +-- 1. load godot-prompter:player-controller    <- unchanged, still authoritative
        +-- 2. deliver it through the mentor contract   <- what is new
```

The skill states explicitly: **load the matching domain skill first, then deliver it through the
contract.** Mentor mode that answers from general knowledge instead of the domain skill is the
primary failure mode and is called out as an anti-pattern in the skill itself.

### B2. The five beats

| Beat | Content |
|---|---|
| **Concept** | The Godot idea, and why this node/API over the alternative |
| **Editor** | The GUI half — Scene dock, Inspector, Project Settings (see Change B4) |
| **Code** | Annotated, GDScript then C#, per repo convention |
| **Verify** | Run it: expected behaviour, likely failure mode, and the fix |
| **Next** | One suggested extension — not five |

Two guards are part of the contract:

- **Explanation, not scope.** Mentor mode explains what was asked for. It does not invent extra
  features in order to have more to teach.
- **Off-ramp.** "just give me the code" / "skip the explanation" drops to normal delivery
  immediately and updates the persisted flag.

**Depth calibration:** `level` (`beginner` | `intermediate`) is asked once on activation and
then remembered. It controls how much of the Concept and Editor beats is spelled out, not
whether they appear.

### B3. State

```json
// .godot-prompter/config.json — project root
{
  "mode": "mentor",
  "level": "beginner",
  "language": "gdscript",
  "godot_version": "4.5",
  "renderer": "Forward Plus"
}
```

- **Written by** the `godot-mentor` skill on activation / off-ramp.
- **Read by** the SessionStart hook. When `mode` is `mentor`, the hook appends a compact
  contract reminder to the injected card, so the mode survives `/clear`, compaction, and
  subagent dispatch — the exact persistence failure that limited the 2026-04-09 fix.
- **Degradation:** on Codex and Antigravity (no hooks) the skill still works; it just does not
  self-restore after a context reset.
- **Git:** the file is safe to commit (a team can share a teaching level). The skill mentions
  this and offers to `.gitignore` it if the user prefers it personal. It does not decide for
  them.

**Activation** is natural-language, via the skill's `description` frontmatter — "teach me as we
go", "I'm learning Godot", "explain while you build", "guide me". This is the only activation
path that behaves identically on all 7 supported platforms.

### B4. Editor guidance — constrained in v1.13.0, full in v1.14.0

The Editor beat is the highest-risk part of mentor mode. Every skill in the repo teaches code;
none teaches GUI. Left unaddressed, editor steps would come from the model's general knowledge
rather than from verified content — precisely the failure mode `CONTRIBUTING.md` already warns
about for addon skills ("research the tag, not the docs site").

Fully grounding the Editor beat requires a researched editor reference, which is a work item
comparable to adding an addon skill. **That research is deferred to v1.14.0** (see "Deferred to
v1.14.0" below). v1.13.0 ships the half that is cheap, useful immediately, and a prerequisite
for the deferred half.

**Ships now — detect the user's actual Godot version.**

The hook already locates `project.godot` to decide whether to fire. That file declares the
version and renderer:

```ini
config/features=PackedStringArray("4.5", "Forward Plus")
```

Both are parsed into `.godot-prompter/config.json`. This is worth shipping on its own merits
even before the editor references exist: renderer choice changes real advice, since Compatibility
mode has no SDFGI and no volumetric fog, so *every* answer improves — not just mentor-mode ones.
It is also the grounding mechanism v1.14.0's editor content will target.

**Ships now — a constrained Editor beat.**

Until the researched references land, the Editor beat is limited to what is derivable from the
Godot API and stable across all of 4.x:

- **Permitted:** node-tree construction (which node types, nesting, naming), Inspector property
  names and values, exported-variable wiring, resource assignment, autoload registration by
  path.
- **Forbidden:** precise menu paths, dock layouts, toolbar/button positions, and any
  version-specific UI chrome. These are what get hallucinated, and they are what moved most
  between 4.3 and 4.7.

The `godot-mentor` skill states this boundary explicitly, so the constraint is enforced by the
skill's own instructions rather than left to the model's discretion. For a beginner, "add a
Node2D named StateMachine and set its `initial_state` export to Idle" is genuinely useful and
verifiable; a confidently wrong click-path is worse than silence.

## Change C — Byte-headroom debt (Pattern X x8)

`CHANGELOG.md` for v1.12.0 warns that 4 skills sit near the 15.5 KB advisory band. Measured
LF-normalized at this baseline, **8 skills have under 100 bytes of headroom**:

| Skill | Bytes | Headroom to 15,872 |
|---|---:|---:|
| `localization` | 15864 | **8** |
| `physics-system` | 15853 | 19 |
| `addon-development` | 15843 | 29 |
| `particles-vfx` | 15837 | 35 |
| `godot-ui` | 15826 | 46 |
| `3d-essentials` | 15813 | 59 |
| `multiplayer-basics` | 15791 | 81 |
| `event-bus` | 15727 | 145 |

Apply Pattern X to each, targeting ~11–13 KB SKILL.md with the overflow in `references/`.
Mechanical and well-understood (35 skills were restructured this way across v1.7.0–v1.7.3).

**No teaching content is removed.** v1.12.0's headroom trim already consumed the easy
whitespace and prose slack; there is nothing left to tighten, so this must be a genuine
Pattern X restructure.

This is also why Change A's zero-byte constraint on domain skills matters: with 8 skills inside
100 bytes, any cross-reference added by this release would trip CI.

## Testing

**Validator (`scripts/validate-skills.mjs`):**
- New `session-card` check: both markers present, correctly ordered, region non-empty, region
  <= 3,072 bytes LF-normalized.
- Fixtures under `scripts/fixtures/session-card-broken/` (missing/empty region) and
  `scripts/fixtures/session-card-oversized/` (region over cap) asserting the check *rejects*
  both cases, consistent with the v1.12.0 validator self-test.

**Hook tests (new):**
- Fires and emits valid JSON inside a directory tree containing `project.godot`.
- Emits nothing and exits 0 outside one.
- Ancestor walk terminates at depth 4.
- All three output shapes parse as valid JSON, with exactly one context field per platform.
- `run-hook.cmd` resolves bash on Windows and exits 0 silently when no bash is found.
- `project.godot` version/renderer parsing handles a missing or malformed `config/features`.

**Agent integration (`tests/agent-integration/TEST_PLAN.md`):**
- Mentor mode wraps the domain skill rather than replacing it (the B1 failure mode).
- Off-ramp phrase drops to normal delivery and updates the config flag.
- **Editor-beat boundary holds:** a prompt that invites a click-path ("where do I click to add
  an autoload?") produces node/Inspector-level guidance, not an invented menu path. This is the
  test that keeps the v1.13.0 constraint honest, and it should keep passing after v1.14.0
  relaxes it — the answer gets fuller, never fabricated.
- Coexistence regression: with Superpowers active in a Godot project, a domain skill is invoked.

**Manual:** verify the hook end-to-end in a real Godot project on Windows, since `run-hook.cmd`
path discovery is the least portable part of the release.

## Risks

| Risk | Mitigation |
|---|---|
| Editor guidance is thinner than a beginner hopes for | Accepted for v1.13.0. The constrained beat is still useful (node tree + Inspector) and is honest about its limits; v1.14.0 lifts it. Wrong click-paths would be worse than fewer instructions |
| Mentor mode ships feeling half-finished without editor research | The five beats all fire; only Beat 2's depth is capped. Version/renderer detection ships now, so v1.14.0 is additive content rather than rework |
| Hook fails silently on an unusual Windows setup | `run-hook.cmd` exits 0 when bash is absent — the plugin degrades to v1.12.0 behaviour rather than breaking the session |
| Injected card grows over time into a context tax | Hard 3 KB target on the card region, asserted by the validator check |
| Mentor mode answers from general knowledge instead of domain skills | Named as the primary anti-pattern in the skill; covered by an agent integration test |
| First release shipping executable code raises install-trust questions | Conditional firing (no-op outside Godot projects), no network access, no writes outside the user's own project, attribution stated openly |

## Deferred to v1.14.0 — the editor research

Split out of this release deliberately. v1.13.0 ships the constrained Editor beat and the
version/renderer detection it will target, so this is **additive content, not rework**.

**Scope when picked up:**

```
skills/godot-mentor/references/
  editor-navigation.md     docks, main-screen tabs, panels; version-flagged 4.3 -> 4.7
  editor-recipes.md        ~20 workflows: add node & attach script, create a custom
                           Resource, Input Map setup, AnimationPlayer track authoring,
                           TileSet/TileMap painting, import presets, autoload
                           registration, export presets, remote scene-tree debugging
docs/superpowers/notes/
  <date>-godot-editor-research.md    research digest
```

**Conventions it must follow** — the same standard as the addon skills in `CONTRIBUTING.md`:
research against pinned Godot releases rather than the docs site, version-flag every UI claim
that moved between 4.3 and 4.7, and ship the digest so the next author knows what was verified
and when. Existing inputs: `2026-07-05-godot-4.7-deltas.md` (39 KB) and
`2026-04-30-godot-4.5-4.6-deltas.md`.

**Landing it:** relax the "Forbidden" list in `godot-mentor/SKILL.md` §Editor beat to permit
click-paths *that the references cover*, keeping the prohibition for anything they do not. The
editor-beat boundary integration test stays — it should still pass, with fuller answers.

Also still deferred, unchanged from v1.12.0/v1.11.0: GodotSteam and Dialogic addon skills, the
raytracing skill (pending API stabilization, ~4.8+), and the migration/upgrade meta-skill.
